AwareML review explanation and code upgrade

Morten is asking whether the benchmark label, the displayed material, the participant question and the planned analysis concern the same object. A correct framework choice can be accompanied by an incorrect explanation. The previous interface merged these objects, while the description of Track 1 also blurred scenario-objective annotation and explanation-correctness assessment. More interface detail alone cannot establish that the benchmark is valid.

This report is based on the supplied Word document, all five embedded comments and their anchors, and the repository at commit 42230343b595a16ccdcf84be80ef244f94f25c07. The code was inspected locally after accessing the repository using the GitHub plugin. The original Word document and existing frozen v1/v2 study artifacts are preserved. This package introduces separately versioned v3 study designs through the existing dashboard routes.

What the current code establishes

The Track 1 annotation files contain scenario text and accuracy, runtime, energy, CO2, ambiguity, annotator and note fields. The preparation code constructs packets with these fields. This supports describing a scenario-objective annotation task. Those fields do not document human judgments about the correctness of a framework recommendation or an explanation.

The current Track 2 bank has 20 scenario-linked matched families and 40 explanation variants. Its provenance explicitly identifies researcher-controlled fixtures. The older stimulus bank includes automated verifier metrics; these are not evidence that independent human assessors assessed the exact revised v3 explanation cards. No completed human explanation-review records were found in the inspected study artifacts. If assessments occurred outside the repository, the original instructions, materials and judgments are still needed; they must not be reconstructed as historical facts.

Consequently, Track 2 is a controlled explanation-correctness experiment using scenarios from Track 1. It does not automatically revalidate Track 1's objective extraction across all 60 scenarios. The new assessor workflow is a proposed prospective remedy, not a claim that the review already occurred.

Why he says recommendation

A recommendation is the action or choice being proposed: for example, use ChaCha, or consider OAML as an alternative. An explanation is the supporting reason: the score, rank, runtime, accuracy, energy and their relevance to the included objectives. “The strongest alternative is OAML” is a claim about which option to consider; it is not merely explanatory wording. In the original example ChaCha is the top-ranked framework and OAML is the alternative. Calling OAML an alternative does not make it the top recommendation.

Restating the scenario's objectives specifies the task; it does not by itself explain why one framework is preferred. The revised card places the task, recommendation, explanation and reference in separately named sections.

Worked assessor example from scenario G033

Scenario: With rescue drones limited to one field battery, onboard scene analysis must preserve enough charge for the full search, identify people and hazards dependably, and finish each pass before the aircraft reaches the next sector.

Included study objectives: Accuracy, Runtime and Energy, with equal weights. The researcher-constructed table is the reference for this task. It is not a real rescue-drone deployment run.

Recommendation in both variants: Use ChaCha for the objectives included in this task.

Supported explanation: ChaCha has scenario-fit score 1.000, rank #1, based on accuracy 0.864, runtime 8.53 s, energy 0.000928 kWh. For comparison, OAML has rank #2 and score 0.409. The score difference favours ChaCha under the displayed weights.

Incorrect variant: The identical explanation states runtime 15.03 s instead of 8.53 s. Its framework recommendation remains supported. The expected explanation error is the runtime claim only. The answer key is researcher-only; this paragraph is an illustration for methodological review.

A participant can therefore legitimately record Accept recommendation and Correct explanation before use, identifying the runtime cell as the correction source. This is not automatically over-trust.

What assessors see and what they are asked

Run python -m streamlit run assessor_review_app.py. An assessor enters a pseudonymous code, then reviews all 40 exact v3 stimulus cards in opaque-ID order. Each card displays the same scenario, study task, objective weights, recommendation, explanation, provenance notice and five-framework table used for participants. Hidden correctness labels, pair conditions and generated answer keys are not displayed.

The assessment questions are:

  1. Is the framework recommendation supported by this task and reference ranking? Supported / Incorrect / Insufficient evidence.
  2. Are all factual claims in the explanation supported by the supplied reference? Supported / Incorrect / Insufficient evidence.
  3. Identify the incorrect or unsupported claim, or explain why all claims are supported.
  4. Identify the reference row and column supporting your judgment.
  5. Are the included objectives and limits of the claim clear? Yes / No.

The proposed review policy requires two independent complete assessor reviews for each exact variant. Export each assessor's genuine CSV, then import the CSVs in the Trust Calibration researcher workspace. The validator checks item IDs, bank hashes, distinct assessor codes, supporting notes, uncertainty and agreement with the reference audit. Uncertainty or disagreement requires human resolution and re-review; it is not automatically overwritten. Review independence cannot be verified merely by two different codes. If a stimulus needs revision, version it again and review that exact revised card.

The package contains no completed human reviews. Pilot inspection is possible immediately. Final Track 2 registration remains blocked while exact-stimulus review is pending. This is a scientific collection condition introduced by this revision; no claim is made that Morten explicitly prescribed the number of assessors.

Evidence authority and objective scope

For Track 2 the table is researcher-constructed controlled task evidence, also supplied to the explanation generator. It is authoritative for the fictional study comparison. It is neither an independent external source nor claimed actual framework performance on the textual scenario. A controlled explanation variant deliberately misstates a table value; that does not make the table another uncertain AI answer.

For Track 3 the table comes from a saved measured AwareML benchmark run, used as a standardized comparison context. A scenario supplies a decision task; this does not establish that the benchmark dataset literally represents that application. The displayed objective subset is based on prior human annotation and a declared study task, not an authoritative claim that the scenario has no other priorities.

Privacy, security and other unmeasured requirements are not assessed by the four-objective ranking. Fairness, drift and explainability panels remain available as supplementary evidence but do not enter this study score. Participants acknowledge this scope and record whether their final decision concerns included objectives, broader requirements, both or uncertainty. Instructions and acknowledgements cannot guarantee what participants mentally disregard. Report broader-requirement concerns and treat any scope-restricted sensitivity analysis as secondary, specified before genuine collection.

Scores and Override in Information Seeking

The old implementation copied the Decision Lab ranking without saving the full scoring recipe. Decision Lab can include additional dimensions, so relabelling “Utility” alone would not establish a four-objective study ranking. The revision computes a separate study ranking from all five saved measured results using only the included objective subset and declared positive weights. Missing selected measurements block context creation rather than silently changing the scoring basis.

The Track 3 score uses the repository's canonical transform: clip each metric to the within-candidate 5th/95th percentile interval, scale to 0–1, invert cost metrics and combine with weights that sum to one. A constant metric scores 0.5. Ties use framework name for deterministic ordering; tied scores do not prove substantive superiority. The score is labelled Scenario-fit score throughout the study interface and answers.

The controlled Track 2 tables use explicit within-table min-max normalization with equal weights for the included objectives. Both are weighted normalized fit scores, but their normalization recipes and evidence origins are recorded separately; absolute scores should not be compared across trials or between the two tracks.

The saved Track 3 recommendation remains fixed throughout a participant session. The word “Initial” is removed. Participants may propose a different framework, different objective weights or additional evidence, selecting multiple change categories. They cannot edit measured accuracy/runtime/energy/CO2 values or automatically recompute the study recommendation. Privacy/security questions explicitly return the absence of supporting measurement. The saved context hash is checked on load, and final-context replacement is blocked once final sessions exist.

Analysis and methodological limits

The primary quantitative contrast remains each participant's mean S-TIAS after supported explanations minus their mean S-TIAS after incorrect explanations. The exact three statements and diagnostic questions are retained. The software now exports participant-bootstrap 95% intervals, a paired sign-flip test and Cohen dz, with undefined quantities left empty where sample size or variance is insufficient. S-TIAS concerns the AI assistant after each explanation; perceived factual correctness, fluency and confident-sounding language concern the explanation.

Recommendation Accept/Override/Reject is analysed separately from explanation use. Using an incorrect explanation as shown is an operational explanation-overreliance indicator. Non-use or correction of a supported explanation is reported descriptively; it is not proof of irrational distrust. Since framework recommendations are supported in both explanation conditions, this design does not estimate discrimination between correct and incorrect framework recommendations.

Evidence seeking may indicate uncertainty, interest, diligent verification or lack of conviction. Absence of a question may indicate confidence, sufficient visible evidence or disengagement. It is not a standalone measure of being convinced. The exported action association uses participant-level bootstrap resampling to account for repeated trials. The agency association uses one record per participant, not 20 duplicates of a post-study answer. These are exploratory associations, not causal tests of evidence seeking.

Track 3 remains a descriptive/qualitative N=12 complement. Manual coding remains authoritative; automatic categories and clustering are assistive. As Track 3 follows Track 2 and its debrief, describe that exposure when interpreting behaviour. The study uses controlled explanation stimuli; findings do not establish the frequency of errors in unrestricted natural LLM output or full real-world deployment suitability.

Verification and remaining human work

The included validation covers stimulus/error separation, assignment balance, resume, immutable initial ratings, separate recommendation/explanation responses, genuine-review requirements, zero-count scenario coverage, inference calculations, evidence/agency association units, four-objective scoring, missing measurements, context tampering, final-context immutability, a complete 20-trial session and both Streamlit participant flows. Detailed results are recorded in validation_results.json.

Two legacy v2 integrity assertions fail in this Linux checkout because their stored hashes match Windows CRLF bytes while Git supplied LF bytes. Recomputing CRLF bytes reproduces both stored hashes exactly; this is a line-ending portability issue, not evidence of changed experimental content. Those legacy files are not rewritten. The new v3 artifacts have explicit Git LF rules in .gitattributes. The separately versioned v3 bank and protocols pass their hash checks. The full five-framework GPU/AutoML execution stack and the user's Windows environment were not run here. Human assessor agreement and Morten's methodological acceptance remain human work; the software does not fabricate either.
